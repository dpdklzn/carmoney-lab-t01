# Spec CASE-08: оценка залога по VIN

Эпик t01; учебные, синтетические правила. Источники: [intent_CASE-08.md](../intent/intent_CASE-08.md), [CASE-08.md](../sources/CASE-08.md). Новые числа — из CASE-08, заполненного по прямому поручению постановщика. Это требования для реализации, а не утверждение о готовом коде.

## Входит / не входит

Входит: синтетический справочник/мок с ценой и характеристиками, оценка со скидками, сверка, обработка отсутствия/сбоев, расчёт LTV с новой базой, контракт двух существующих API, сохранение nullable-оценки и причин. Конфигурация параметров, тестовые часы и миграция допускаются как необходимые способы реализации.

Не входит: реальные данные/интеграции, изменение общих порогов LTV, fallback-оценки, повторные обращения, изменение frontend/дизайна. Изменение запроса equipment — явное расширение API; старая форма без этого поля не поддерживает новый контракт и требует отдельной задачи. Существующие проверки VIN/суммы/срока/года/пробега сохраняются.

## Общие условия AC

Другие поля заявки валидны. Год в тестах фиксируется как 2026 из CASE-08 §3; в работе используется календарный год сервиса. Цена для граничных примеров B=1000000 ₽, оборудование BASE, если не указано иначе. «Граница ±1» — минимальная единица км/года/мс, производная от источника, а не новый бизнес-порог. API-критерии проверяются на обоих путях; сохранение — на /api/applications. Мок не вызывает реальные сервисы.

## Требования и критерии приёмки

### REQ-CASE-08-01

**Данные по VIN**

Сервис запрашивает ровно указанный VIN и получает базовую цену, год, пробег и комплектацию из синтетического справочника; не получает цену из произвольной другой записи.
Источник: intent «Замысел»; CASE-08 §1, П-1/П-3.

- **AC-CASE-08-01.** Given найденная синтетическая запись E-01. When обрабатывается заявка с её VIN. Then для оценки используются данные этой записи; мок подтверждает обращение с тем же VIN.
- **AC-CASE-08-02.** Given неизвестный VIN или ответ с отсутствующей ценой/годом/пробегом/комплектацией. When выполняется запрос. Then отсутствующий VIN обрабатывается по AC-09, некорректная запись — по AC-11; данные соседнего VIN и стоимость заявки не подставляются.

### REQ-CASE-08-02

**Расчёт залоговой стоимости**

По справочным пробегу и возрасту выбирается ровно одна скидка каждого вида и вычисляется B×(1−dM−dA), затем один раз half-up до целого рубля. Данные заявки не заменяют справочные при выборе скидок.
Источник: intent Constraints; CASE-08 П-1, SIM-REG-CASE08, DEC-08-01.

- **AC-CASE-08-03.** Given M =0, 99999, 100000, 100001, 199999, 200000, 200001, 299999, 300000, 300001, 500000; A=3. Then dM соответственно 0/0/0/5/5/5/10/10/10/15/15%. При B=1000000 результат соответственно 1000000/950000/900000/850000 для четырёх групп; скидка возраста нулевая. Источник: таблица П-1; соседние значения производные.
- **AC-CASE-08-04.** Given A =0, 2, 3, 4, 6, 7, 8, 11, 12, 13, 20; M=0. Then dA соответственно 0/0/0/5/5/5/10/10/10/20/20%. Значения 3/7/12/20 включены в меньшую скидку. Источник: П-1.
- **AC-CASE-08-05.** Given A=8, M=200001, B=1000000. Then V=800000: сумма скидок 10%+10%, не последовательное перемножение. Given B=100001, dM=dA=5%. Then V=90001. Given B=100005 при тех же скидках. Then V=90005 (90004.5 округляется half-up). Первый пример из §3 E-03, округление из П-1; последний вход — синтетический граничный тест правила округления.
- **AC-CASE-08-06.** Given справочные характеристики E-01 и другие, но допустимые характеристики заявки. When рассчитывается V. Then V=1000000 независимо от market_value=2000000 и несогласованных характеристик заявки; сверка влияет на решение отдельно.

### REQ-CASE-08-03

**Сверка характеристик**

Проверять абсолютную разницу пробега, точный год и точный идентификатор комплектации; возвращать все причины расхождений. Delta≤10000 допустимо, больше — расхождение.
Источник: интервью; CASE-08 П-2, DEC-08-02.

- **AC-CASE-08-07.** Given справочный пробег 150000. For пробег заявки 140001/140000/139999 и 159999/160000/160001 Delta=9999/10000/10001 в обоих направлениях. Then первые два значения каждого ряда не создают причину, третье создаёт «Расхождение пробега превышает допустимый порог». При исходном approve только третье переводит в review. Источник порога: П-2; пары — синтетические примеры абсолютной разницы.
- **AC-CASE-08-08.** Given E-01. When год заявки не равен 2023 либо equipment не равен BASE. Then соответствующая причина «Год выпуска не совпадает со справочником» или «Комплектация не совпадает со справочником» возвращается. При одновременных расхождениях все причины перечислены в порядке пробег, год, комплектация; совпадение не создаёт причины.

### REQ-CASE-08-04

**Не выдавать оценку при отсутствии или сбое данных**

Неизвестный VIN, некорректный ответ, сбой/таймаут дают review с причиной и null оценкой/LTV, без fallback и автоматических повторов.
Источник: исходный П-3, интервью; CASE-08 П-3/П-4, DEC-08-03/04.

- **AC-CASE-08-09.** Given VIN E-06 не найден. Then decision=review, collateral_value=null, ltv=null, approved_limit=0, причина «Нет данных по VIN в справочнике». Даже при положительном market_value заявки эти поля не заменяются числами.
- **AC-CASE-08-10.** Given управляемое время ответа t=1499/1500/1501 мс. Then при 1499 валидный ответ используется, при 1500/1501 результат review/null/null с причиной «Справочник не ответил вовремя». Только одна попытка; поздний ответ не меняет результат. Источник: П-4; тесты без реального ожидания.
- **AC-CASE-08-11.** Given отсутствующее/null поле, пустая комплектация, нецелая/отрицательная цена или пробег, B=0, возраст -1/21 либо пробег -1/500001 в ответе справочника. Then review/null/null, причина «Данные справочника неполные или некорректные». A=0/20 и M=0/500000 в валидной записи не отклоняются. Источник: П-3; соседние значения — производные.
- **AC-CASE-08-12.** Given ошибка транспорта/сервиса или невалидная итоговая стоимость. Then review/null/null с причиной некорректных данных; нет повторного запроса или приблизительного расчёта. Ошибка ввода заявки при этом остаётся отдельным случаем AC-18/19.

### REQ-CASE-08-05

**Решение и лимит по новой базе LTV**

Использовать V, а не market_value заявки, сохраняя текущие сравнения LTV и приоритет reject; сверка переводит только approve в review. При approve лимит равен сумме, иначе 0.
Источник: intent; CASE-08 П-2/П-5, интервью; фактический командный DecisionEngine и AssessmentService.

- **AC-CASE-08-13.** Given E-01 с суммой 500000, V=1000000, market_value=2000000. Then LTV=50%, не 25%; approve и лимит 500000. Given E-02. Then LTV=52.63%. Источник: §3; расчёт П-5.
- **AC-CASE-08-14.** Given V=1000000, суммы 599900/600000/850000/850100 (валидные по текущему конфигу). Then LTV=59.99/60/85/85.01%, решения approve/review/review/reject. Источник: текущие пороги П-5, суммы вычислены как V×LTV/100.
- **AC-CASE-08-15.** Given Delta>10000 и исходные LTV-решения approve/review/reject. Then итог review/review/reject. E-04 даёт review, E-05 — reject с сохранённой причиной расхождения. Источник: интервью, §3, П-2/П-5.
- **AC-CASE-08-16.** Given случаи approve/review/reject. Then approved_limit равен сумме только при approve и равен 0 при review/reject, включая невозможность оценки. Существующие пороги LTV и другие правила не ослаблены.
- **AC-CASE-08-17.** Given отсутствующий VIN или таймаут. Then LTV не вычисляется и сравнение с reject-порогом не производится; review обусловлен невозможностью оценки, а не числом 0 или стоимостью заявки.

### REQ-CASE-08-06

**Валидировать заявку до обращения к зависимости**

Сохранять прежнюю валидацию заявки и проверять новую обязательную непустую строку equipment. Невалидная заявка не вызывает справочник.
Источник: CASE-08 П-6, DEC-08-05; существующий валидатор.

- **AC-CASE-08-18.** Given equipment отсутствует/null/пустая строка/нестроковое значение. Then HTTP422 с ошибкой equipment, справочник не вызван. Непустой неизвестный идентификатор не даёт ошибку ввода сам по себе: при сравнении с известной записью это расхождение.
- **AC-CASE-08-19.** Given невалидные VIN, год, стоимость заявки, сумма, срок или пробег по текущим правилам. Then прежняя ошибка HTTP422 сохранена. Границы mileage=0/500000 допускаются, -1/500001 не допускаются. Источник: текущий конфиг и П-6.

### REQ-CASE-08-07

**Контракт API оценки**

Оба существующих пути возвращают V/LTV/решение/лимит/причины, сохраняя другие поля; отсутствие оценки представляется null, не 0. Для валидного запроса сбой справочника — результат review, не ошибка HTTP-зависимости.
Источник: интервью, CASE-08 П-6, DEC-08-05.

- **AC-CASE-08-20.** Given валидная заявка. When POST /api/ltv. Then HTTP200, collateral_value (целое/null), ltv (число/null), decision, approved_limit, assessment_reasons и прежний vehicle_age. Нет id и записи заявки. When POST /api/applications. Then HTTP201 с теми же результатами и id созданной заявки.
- **AC-CASE-08-21.** Given AC-09/10/11/12. Then оба пути возвращают review, null-поля и точную причину; не HTTP504 и не пустое успешное approve. Для совпадения без проблем assessment_reasons=[]; расхождения включаются и при reject. Источники строк: П-2..П-4.

### REQ-CASE-08-08

**Сохранять неизвестную оценку без выдуманных чисел**

Сохранять решение заявки, оценку, LTV и причины с их действительными значениями, включая null. Не терять уже сохранённые записи при расширении хранения.
Источник: CASE-08 П-6, DEC-08-05; текущая схема требует изменения для nullable LTV.

- **AC-CASE-08-22.** Given создание найденной заявки E-01 и отсутствующего VIN E-06. Then повторное чтение записи сохраняет соответственно V=1000000/LTV=50 и V=null/LTV=null, причины и решение. Исходные данные заявки не подменены оценкой справочника.
- **AC-CASE-08-23.** Given база с прежними решениями до изменения схемы. When применена штатная миграция. Then количество и прежние значения заявок/решений сохраняются, новые записи принимают null; сброс базы не используется.

## Разбор открытых вопросов

OQ-01..04 intent закрыты учебными решениями DEC-08-01..05 в CASE-08 §6 по поручению пользователя. Конфликты синтетических источников явно разрешены для этого варианта, не молчаливо. Технические решения хранения/мока не добавляют новых бизнес-правил. Автоматические повторы, fallback, изменение общих порогов и UI вне scope.
